## 代码中会放大波动的环节

1. `app/downloader.py` 的 `resolve_douyin_share_url` 遇到 HTTP/网络异常会返回原短链，丢弃该阶段错误。后续 yt-dlp 再请求短链失败时，定位信息只剩下载器错误。
2. 普通视频的备用解析只在日志含 `fresh cookies` 或 `http error 403` 时触发。纯连接重置不触发重新解析与整条链路重试。已有 `--retries 3` 不能据此视为所有网页提取阶段都重试了；历史失败日志没有该阶段成功重试的证据。
3. `_resolve_douyin_video_media` 返回第一个可信地址，后续地址连接失败后没有轮换详情中其他候选地址。每个任务仅追加一次备用下载。
4. 本机 yt-dlp 版本为 `2026.8.19`；其 Douyin 提取器在详情为空或请求失败后统一提示需要新 Cookie。这个提示不能单独证明 Cookie 已过期。

## 为什么无法还原 11 号下午

`qq_bot/run.py` 配置每 2 MB 轮转、仅保留 3 份历史日志，当前大量 DEBUG 事件使保存范围只覆盖数小时。排查开始时最早一份从 10 月 12 日 20:14:10 开始；NapCat 的日志目录没有可用于补齐该时段的日志。

`app/main.py` 处理已知下载失败时只更新内存 JobStore，没有写入持久的任务失败记录。JobStore 重启后丢失，终态任务还会按 TTL 清理，无法从视频 API 中还原两天前的错误。

建议后续修复：为短链/详情/媒体阶段保留独立且脱敏的持久诊断记录；对超时、连接重置和部分临时 HTTP 错误进行有界重试，并在必要时重新解析与尝试其他可信媒体地址。仅凭当前证据，不建议将重新导出 Cookie 作为唯一修复。
